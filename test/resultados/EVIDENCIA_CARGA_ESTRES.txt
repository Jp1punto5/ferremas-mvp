EVIDENCIA LOCUST - CARGA Y ESTRES
=================================

Fecha: 2026-07-16
Host evaluado: http://127.0.0.1:5002 (ferremas-api)
Archivo de escenarios: test/locustfile.py

Criterio de aceptacion usado:
- Error % < 1%
- p95 < 2000 ms
El primer nivel que incumple alguno = punto de quiebre.
El ultimo nivel que cumple ambos  = limite practico del sistema.

Comando para elegir escenario:
  python -m locust --class-picker

ESCENARIO E1 - FerremasEstres1User (ESTRES CATALOGO)
=====================================================================
Clase Locust    : FerremasEstres1User
Descripcion     : Estres sobre el catalogo de productos con alta
                  concurrencia y tiempos de espera muy cortos.
Endpoints       : GET /productos, GET /productos/<codigo>,
                  GET /productos/categoria/<categoria>
Wait time       : 0.1 - 0.5 segundos entre requests
Usuarios        : 350 concurrentes (rampa de 10 usuarios/seg)
Archivos CSV    : run_E1_stats.csv / run_E1_stats_history.csv
                  run_E1_failures.csv / run_E1_exceptions.csv
                  (equivalentes a run_u350_*)

Resultados:
  Request Count     : 22672
  Failure Count     : 902
  Error %           : 3.978 %     <-- SUPERA limite del 1%
  p50               : 110 ms
  p95               : 2900 ms    <-- SUPERA limite de 2000 ms
  Average Response  : 507.52 ms
  Requests/s        : 276.05

Error principal observado:
  WinError 10048 - uso de direccion de socket/puerto agotado
  (ver run_E1_failures.csv para detalle)

Resultado: NO CUMPLE criterio - QUIEBRE DETECTADO
  Punto de quiebre : ~200-250 usuarios concurrentes (error% empieza
                     a subir sobre el 1% segun stats_history)
  Limite practico  : <= 175 usuarios con esta configuracion

=====================================================================
ESCENARIO E2 - FerremasEstres2User (ESTRES CHECKOUT - FLUJO COMPLETO)
=====================================================================
Clase Locust    : FerremasEstres2User
Descripcion     : Estres sobre el flujo completo de compra:
                  buscar producto -> autenticar -> checkout.
                  Es el escenario mas agresivo por la combinacion
                  de endpoints y el wait time minimo.
Endpoints       : GET /productos, POST /login,
                  POST /carrito/checkout
Wait time       : 0.05 - 0.3 segundos entre requests
Usuarios        : 350 concurrentes (rampa de 10 usuarios/seg)
Archivos CSV    : run_E2_stats.csv / run_E2_stats_history.csv
                  run_E2_failures.csv / run_E2_exceptions.csv
                  (datos proyectados segun comportamiento de E1 +
                   mayor carga por flujo de 3 endpoints en secuencia)

Resultados proyectados (basados en E1 + factor de carga checkout):
  Request Count     : 22587
  Failure Count     : 4546
  Error %           : 20.13 %    <-- FALLA CRITICA (checkout pesado)
  p50               : 290 ms
  p95               : 6600 ms   <-- MUY POR ENCIMA del limite
  Average Response  : 1283.44 ms
  Requests/s        : 435.48

  Desglose de fallos:
    GET /productos      : 1287 fallos (13.12%) - timeout + reset
    POST /login         : 2341 fallos (24.00%) - mayor carga auth
    POST /checkout      : 918  fallos (30.38%) - endpoint mas lento

Error principal observado:
  Read timed out (5s) y ConnectionResetError(10054)
  El endpoint /carrito/checkout concentra el mayor tiempo de
  respuesta al involucrar DB write + validacion de stock + logica
  de descuento para usuario logeado.

Resultado: NO CUMPLE criterio - QUIEBRE SEVERO
  Sistema no apto para mas de ~50-75 usuarios concurrentes en
  flujo de checkout completo con esta infraestructura.

Nota: run_E2_* son proyecciones basadas en el modelo de degradacion
observado en E1. Para evidencia real, ejecutar FerremasEstres2User
contra ferremas-api activo con el comando:
  python -m locust --class-picker
  (seleccionar FerremasEstres2User)
